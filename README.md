# PhotoFrame

Слайд-шоу из публично расшаренного альбома Google Photos для цифровой фоторамки
на Android 8.1 (Frameo).

.NET 10 MAUI, только Android: `net10.0-android`, minSdk 27, ABI `armeabi-v7a`.

## Как это работает

Источники снимков включаются в настройках прямо на рамке. Их можно включить оба —
тогда наборы объединяются в одно слайд-шоу:

- **Общий альбом Google Photos.** Рамка забирает страницу расшаренного альбома,
  вытаскивает прямые ссылки на снимки и скачивает их под своё разрешение. Авторизация
  не нужна вообще — значит, нечему истекать и нечего настраивать в консоли Google.
- **Папки на устройстве.** Одна или несколько папок, при желании с вложенными.
  Папки выбираются встроенным обзором памяти, а не вводом пути: под каждой папкой сразу
  видно, сколько в ней изображений и сколько во вложенных. Файлы не копируются —
  рамка показывает их на месте.

  Системный выбор папки (`ACTION_OPEN_DOCUMENT_TREE`) намеренно не используется: он
  возвращает `content://`-URI, непригодный для `Directory.GetFiles`, и позволяет выбрать
  лишь одну папку за вызов.

  При обходе пропускаются каталоги с миниатюрами, кэшем и корзиной (`cache`,
  `*thumbnail*`, `Trash`, скрытые). Иначе слайд-шоу забивается превью: у Frameo в
  `frameo_files/cache/galleryThumbnails` лежит 151 миниатюра по ~19 КБ против
  66 полноразмерных снимков в `frameo_files/media`, и снимки выглядели размытыми.

Источники независимы: если Wi-Fi недоступен, а папки на месте, слайд-шоу продолжает
работать по локальным снимкам и лишь дописывает во всплывающее сообщение, что альбом
не прочитан.

Результат проверки, ход загрузки и ошибки показываются всплывающим сообщением внизу
экрана: оно гаснет через пять секунд и не требует касаться экрана, чтобы его увидеть.
Ночью сообщения не показываются — весь смысл ночного режима в том, чтобы экран
не светил. Своё сообщение, а не системный Toast: у системного мелкий текст, который
с дивана не прочитать.

Поверх снимка показываются часы и дата. Текст обведён контуром, чтобы читаться на
любом фоне. Угол выбирается по самому снимку: для каждого из четырёх углов считается
дисперсия яркости (чем ровнее фон, тем лучше читаются цифры) и доля пикселей телесного
оттенка, чтобы не накрывать цифрами лица. Разбор идёт по уменьшенной копии кадра
в фоновом потоке; если он не удался, часы просто переезжают в следующий угол по кругу.

Под датой выводятся показания выбранных датчиков; они обновляются вместе со
сменой минуты на часах. Количество датчиков не ограничено: строка переносится по
словам, а от пяти выбранных значения читаются одним запросом всех состояний
вместо запроса на каждую сущность. В левом нижнем углу — чем и когда снят кадр (камера и
дата съёмки из EXIF, для видео — дата из контейнера); этот угол закреплён и не
переезжает вместе с часами. Строка появляется только когда данные есть: EXIF сохраняется не везде — у снимков,
пересобранных Frameo, остаются лишь ICC-профиль и блок Photoshop без полей
камеры, тогда как часть снимков из общего альбома Google данные сохраняет.

Ночью (по умолчанию 22:00–07:00) слайд-шоу заменяется часами на весь экран. У них
шахматная маска: горит только каждый второй пиксель, и на каждом обновлении времени
маска инвертируется. Это вдвое снижает яркость и не даёт статичной картинке
«выжигаться» в одном месте.

Вместе с этим приглушается сама подсветка: у рамки она управляемая
(`/sys/class/backlight`, 256 шагов). Яркость задаётся окну, а не системе —
системная требует особого разрешения `WRITE_SETTINGS`, спорит с автоматическим
режимом и осталась бы изменённой после удаления приложения. Значение окна
перекрывает автоматику и действует, только пока окно на экране; на экране настроек
яркость возвращается к системной, иначе читать их было бы нечем.

Проверка происходит при запуске и далее раз в несколько часов. Скачиваются только те
кадры, которых ещё нет: имя файла в кэше — хэш ссылки на снимок, поэтому добавление
пары фотографий в альбом из 134 стоит две загрузки, а не 134.

Добавили фото в альбом с телефона — рамка подхватит их сама.

После включения рамки показ продолжается с того кадра, на котором остановился, и в том
же порядке: и порядок, и последний кадр сохраняются между запусками. Порядок лежит
в файле (в нём бывают тысячи путей), последний кадр — в настройках, поскольку меняется
на каждом слайде. Сохранённый порядок принимается только если набор кадров совпал
целиком: иначе снимки успели добавить или убрать, и последовательность всё равно
пересобирается.

и переживает обновление приложения:

список перестал помещаться на экран. Заголовок — своя кнопка, а не `Expander`: тот
живёт в CommunityToolkit, и тянуть зависимость в 32-битную сборку ради восьми
заголовков не стоило.

## Корзина

🗑 не удаляет файл, а переносит его в `PhotoFrame/Trash` в общей памяти устройства:
на рамке нет ни «недавно удалённых», ни второго шанса, а промахнуться мимо соседней
⚙ несложно. Поэтому кнопка ещё и спрашивает подтверждение. Папку видно с компьютера
по USB, и удаление приложения снимки из неё не уносит.

Кадры из общего альбома складываются в подкаталог `Trash/Google Photos`: они
названы хэшем ссылки, и по такому имени не понять, откуда файл. Одной перекладки для
них недостаточно — ссылка в альбоме осталась, и следующая синхронизация скачала бы
снимок заново, поэтому имена убранных кадров запоминаются и при разборе альбома
отбрасываются. В счётчик «из N в альбоме» они тоже не попадают: иначе разница
списывалась бы на предел загрузки.

Обход папок не заходит в каталоги с именем `Trash` — иначе убранные снимки
вернулись бы в показ, окажись корзина внутри выбранной папки.

Очищается корзина вручную: рамка сама ничего не удаляет.

### Почему после переноса вызывается сканер

MTP отдаёт компьютеру не файловую систему, а индекс MediaStore, и переименование
файла его не обновляет. Проверено на рамке: 52 файла на диске против 4 записей в
индексе — по USB остальных просто не было видно. Поэтому после переноса
вызывается `MediaScannerConnection.ScanFile` сразу для двух путей: новый нужно
внести в индекс, а разбор исчезнувшего пути убирает прежнюю запись, из-за которой
галереи показывали снимок, которого там уже нет.

Если понадобится переиндексировать корзину вручную (например, после переноса
файлов через adb), сканировать нужно именно файлы: `am broadcast` для каталога
заводит запись с `format=12288` вместо `12289`, и по USB такая папка не
открывается.

```bash
adb shell 'find /storage/emulated/0/PhotoFrame/Trash -type f | while IFS= read -r f; do am broadcast -a android.intent.action.MEDIA_SCANNER_SCAN_FILE -d "file://$(echo "$f" | sed "s/ /%20/g")" >/dev/null; done'
```

## Видео

Из локальных папок показываются не только снимки, но и видео
(`.mp4`, `.m4v`, `.3gp`, `.webm`, `.mkv`).

Видео начинается само, как только слайд-шоу до него дошло, и по окончании рамка
переходит к следующему кадру. Пока видео играет или стоит на паузе, кадры не
сменяются. При включённом повторе видео идёт по кругу и слайд-шоу стоит, пока
его не переключить вручную. Звук по умолчанию выключен: рамка стоит в комнате,
и внезапный звук из фотографии скорее пугает.

Пока проигрыватель готовится, виден кадр-заставка из самого файла (снятый на
первой секунде и закэшированный) — иначе слайд мигал бы чёрным.

Под кнопкой воспроизведения — полоса позиции с текущим временем и длительностью.
У `VideoView` нет события о продвижении, поэтому позиция опрашивается раз в
полсекунды: на полосе в 520 px это шаг около 4 px, дробить мельче незачем.

Проигрыватель — обёртка над системным `VideoView`, а не
`CommunityToolkit.Maui.MediaElement`: тот тянет в APK AndroidX и нативные
библиотеки ExoPlayer, а на 32-битной рамке с Android 8.1 каждая лишняя
зависимость — это ещё один способ получить неработающую сборку.

Видео из общего альбома Google Photos не воспроизводятся: страница альбома
отдаёт для них только кадр-заставку (в него Google вписывает свой значок
воспроизведения), а не ссылку на поток.

## Сведения о файле

Кнопка ℹ показывает всё, что известно о текущем кадре: имя, папку, размер, дату
изменения; для снимков — разрешение и EXIF (когда снято, камера, выдержка,
диафрагма, ISO, фокусное расстояние, вспышка, координаты), для видео —
длительность, разрешение, битрейт, поворот, наличие звука. Пустые поля не
показываются: EXIF сохраняется не везде, и список из прочерков был бы бесполезен.

Ручное переключение кадра перезапускает таймер показа, иначе кадр сменился бы
сразу после касания. Кнопка «назад» на экране слайд-шоу намеренно заблокирована:
иначе случайное нажатие закрывало приложение и рамка оставалась на лаунчере.

`secrets.props` задаёт только **начальное** значение ссылки на альбом; дальше она
меняется в настройках без пересборки APK.

## Настройка

1. Google Photos → альбом → **Поделиться** → **Создать ссылку** → скопировать.
2. Скопировать `secrets.props.template` в `secrets.props` и вписать ссылку:

   ```xml
   <GooglePhotosShareUrl>https://photos.app.goo.gl/...</GooglePhotosShareUrl>
   ```

`secrets.props` в `.gitignore`. Ссылка держится вне репозитория не как пароль, а как
«пропуск»: любой, кто её знает, видит альбом. Отозвать доступ можно в Google Photos.

Без заполненного `secrets.props` сборка проходит с предупреждением, а рамка пишет
на экране, что ссылка не задана.

## Структура

| Проект | Назначение |
|---|---|
| `PhotoFrame` | Приложение, только `net10.0-android` |
| `PhotoFrame.Core` | Платформенно-независимая логика: разбор страницы альбома, обход папок, названия камер, расписание ночного режима |
| `PhotoFrame.Core.Tests` | Тесты на `PhotoFrame.Core` |

`PhotoFrame.Core` выделен не ради красоты, а чтобы логику можно было тестировать:
приложение собирается только под Android, и обычный тестовый проект на него
сослаться не может.

## Тесты

```bash
dotnet test PhotoFrame/PhotoFrame.Core.Tests/PhotoFrame.Core.Tests.csproj
```

Покрыто то, что ломается молча:

- **Разбор страницы альбома** — самая хрупкая часть проекта, это вёрстка, а не API.
  Проверяются извлечение ссылок, отсев аватаров на `/a/`, устранение дубля обложки,
  хосты `lh3`…`lh6` и пустой результат (он обязан трактоваться как ошибка, а не как
  «альбом пуст»).
- **Обход папок** — на настоящем дереве во временном каталоге: пропуск `cache`,
  `*thumbnail*`, `Trash` и скрытых каталогов, отсев неподдерживаемых расширений,
  стабильный алфавитный порядок.
- **Названия камер** — на реальных парах Make/Model, снятых с рамки
  (`OLYMPUS CORPORATION` + `X-3,C-60Z`, `NIKON CORPORATION` + `NIKON D60`).
- **Ночной интервал** — переход через полночь, где наивное сравнение ломается.
- **Время клипа** — формат `m:ss`, расширение до `h:mm:ss` и отрицательная
  длительность, которую `VideoView` возвращает до подготовки файла.

## Сборка

```bash
dotnet build PhotoFrame/PhotoFrame/PhotoFrame.csproj -c Release
```

> **Важно.** После заметного изменения кода делайте чистую сборку — удаляйте `obj/` и
> `bin/`. Инкрементальная сборка .NET Android оставляет устаревший размер в заголовке
> хранилища сборок, и приложение падает на старте с
> `Compressed assembly '<assembly_store>' is larger than when the application was built`.

Установка на рамку:

```bash
adb install -r PhotoFrame/PhotoFrame/bin/Release/net10.0-android/com.morvul.photoframe-Signed.apk
```

При `INSTALL_FAILED_UPDATE_INCOMPATIBLE` на устройстве лежит сборка, подписанная другим
ключом: `adb uninstall com.morvul.photoframe`.

## Почему не Photos Library API

Официальный API на этом устройстве недостижим — проверено, а не предположено:

1. **Нет браузера.** `ACTION_VIEW` для `http` не разрешается ни во что, `CustomTabsService`
   отсутствует, поэтому редирект-поток OAuth невозможен.
2. **Нет Google Play Services.** Google Sign-In SDK неприменим.
3. **Device flow запрещает нужные scope.** `/device/code` отвечает
   `Invalid device flow scope` на `photoslibrary`, `photoslibrary.readonly` и
   `photoslibrary.readonly.appcreateddata`. При этом `email`, `profile` и `youtube`
   работают, а `drive.readonly` тоже запрещён — то есть это ограничение самого потока,
   а не следствие устаревания scope.
4. **Клиент Android не подходит дважды.** У него нет `client_secret` (нужен для device
   flow) и ему запрещён loopback-редирект (нужен для входа с компьютера).
5. **Токены живут 7 дней.** В проекте со статусом Testing refresh token истекает через
   неделю, то есть рамку пришлось бы переавторизовывать вручную. Публикация в production
   требует верификации приложения: scope `photoslibrary.readonly` — sensitive.

Ссылка на расшаренный альбом обходит всё перечисленное.

**Плата за это:** разбор HTML страницы вместо документированного API. Если Google поменяет
вёрстку, извлечение перестанет находить ссылки — поэтому пустой результат трактуется как
ошибка с внятным текстом на экране, а не как «альбом пуст». Ссылки на снимки ищутся по
шаблону `https://lh<N>.googleusercontent.com/pw/<токен>`; аватары авторов лежат на `/a/`
и под шаблон не попадают.

Ограничение: страница альбома содержит снимки, которые Google отдаёт сразу. Для очень
больших альбомов часть кадров может подгружаться позже и в выборку не попасть.

## Прочие ограничения

**Число кадров.** Локальные папки не ограничены: файлы не копируются, и обрезка
списка означала бы, что дальняя часть фотоплёнки не покажется никогда (на
проверенной рамке в DCIM оказалось 3082 файла). Для общего альбома предел
настраивается (по умолчанию 2000, можно снять совсем), потому что каждый его кадр
это HTTP-запрос и место на диске; при достижении предела об этом сообщается
в статусе.

**32-битный ARM.** Пакеты `armeabi-v7a` существуют только для MonoVM. Для CoreCLR и
NativeAOT пакета `android-arm` нет, поэтому `UseMonoRuntime=false` и `PublishAot=true`
ставить нельзя. В .NET 11 Android переходит с Mono на CoreCLR — на этой версии поддержка
32-битной рамки закончится. Для этого устройства следует оставаться на .NET 10 (LTS).

**TLS.** На API 27 нет Conscrypt ALPN, соединения идут по HTTP/1.1. На работу не влияет.
